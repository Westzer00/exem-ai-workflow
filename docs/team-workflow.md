# 보이스피싱·스미싱 팀 워크플로우

**이 문서는 5인 팀 전체의 설계 방향을 설명합니다. 특정 노드 전체를 개인이 단독 구현했다고 주장하지 않습니다.**

## 보이스피싱
검증된 전사 → 유형 분류 → 유사사례 검색 → 검색 후보 검증 → 근거 사용 범위 계획 → 유형에 맞춘 생성 → 내용 검증 → 표현 조정 → 최종 검증.

처음에는 검색 결과를 바로 생성에 전달했지만, **유사도가 높아도 실제로 활용하기 좋은 근거는 아닐 수 있다는 문제**가 있었습니다. 팀은 근거 선택과 생성 계획을 분리하고 생성 후에도 검증 단계를 두었습니다.

## 스미싱
입력 문자 정리 → 메타데이터·유사사례 확인 → 원본 검증 → 통과한 경우에만 생성 → 생성 결과 검증.

업무상 검증 실패와 워크플로우 자체 실행 오류를 구분해 결과로 전달하도록 설계했습니다.

## 운영 화면과의 연결
사용자는 내부 노드보다 **입력·상태·검증 결과·다음 조치**를 확인해야 하므로 PHISIGHT 화면은 이 순서로 정보를 보여주도록 설계됐습니다.

최종 팀 발표에서 요약한 흐름이며, 기업의 실제 프롬프트·워크플로우 캡처·운영 데이터를 여기에 재배포하지 않습니다.
