# 보이스피싱·스미싱 팀 워크플로우

## 보이스피싱
검증된 전사 → 유형 분류 → 유사사례 검색 → 검색 후보 검증 → 근거 사용 범위 계획 → 유형에 맞춘 생성 → 내용 검증 → 표현 조정 → 최종 검증.

처음에는 검색 결과를 바로 생성에 전달했지만, **유사도가 높아도 실제로 활용하기 좋은 근거는 아닐 수 있다는 문제**가 있었습니다. 팀은 근거 선택과 생성 계획을 분리하고 생성 후에도 검증 단계를 두었습니다.

## 스미싱
입력 문자 정리 → 메타데이터·유사사례 확인 → 원본 검증 → 통과한 경우에만 생성 → 생성 결과 검증.

업무상 검증 실패와 워크플로우 자체 실행 오류를 구분해 결과로 전달하도록 설계했습니다.

## 팀 최종 발표에서 제시한 규모

| 데이터·결과 | 규모 | 기준 |
| --- | ---: | --- |
| 보이스피싱 음성 | **511건** | 음성인식·오류 선별 대상 |
| 보이스피싱 검증 데이터 | **398건** | 사람 검토 후 확정한 팀 데이터셋 |
| 보이스피싱 변형 시나리오 | **1,500건** | 유형별 생성 결과로 발표한 팀 성과 |
| 스미싱 최종 데이터셋 | **5,279건** | 정제·분류·증강·검수를 거친 팀 전체 결과 |
| 스미싱 분류 | **대분류 9개·중분류 26개** | 최종 발표 분류 기준 |

*최종 발표 기준 팀 전체 산출물. 음성 STT 검수와 LOOP 개선의 개인 담당 범위는 [기여 내역](contribution.md)에 별도 표기.*

## 검증 결과와 후속 과제

- 생성 결과를 독립 LLM Judge로 다시 점검하지만 Judge 역시 오판할 수 있습니다.
- 실제 공공기관 실무자가 현장 활용성을 검증한 기록은 발표에서 완료된 결과로 제시되지 않았습니다.
- 환각 감소율, 중복 감소율, 검색 정확도와 같은 **기존 방식 대비 정량적 우수성은 충분히 측정되지 않았습니다.**
- 새로운 범죄 유형이나 근거 데이터가 희박한 유형은 기존 분류·검색 구조에 한계가 있습니다.

## 팀 시연 화면과의 연결
사용자는 내부 노드보다 **입력·상태·검증 결과·다음 조치**를 확인해야 하므로 PHISIGHT 화면은 이 순서로 정보를 보여주도록 설계됐습니다.
